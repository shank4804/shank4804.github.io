Product Insights #2: Jev and the Case for Decision Models

A lot of the work inside an AI application comes down to small decisions. Which team should handle this ticket? Which tool should run next? Is there enough information to proceed?

What caught my attention about Jev from TypeSafe AI is that it makes those decisions the product. You give it context and defined questions. It returns structured answers that software can use directly.

After Hebbia, I wanted to look at another company changing how software uses AI. This time, the interesting interface is an API.

The idea behind Jev

TypeSafe cofounder Diogo Almeida contributed to InstructGPT and RLHF, part of the research behind ChatGPT. His launch post starts with a question I find useful: why has progress in conversational AI not translated into more dependable automation?

The company calls Jev a System One model, borrowing from Daniel Kahneman’s distinction between fast, intuitive judgments and slower, deliberate reasoning. The intended role is a focused judgment inside a larger workflow. More involved reasoning can be handed to another model or a person. TypeSafe’s overview explains that framing.

That division of labor makes sense to me. An application needs different kinds of intelligence at different steps. Deciding where a request belongs and investigating the underlying problem are different jobs.

The problem: Small decisions add up

Imagine a support workflow that reads an email, identifies the issue, checks urgency, and routes it to a team. Only after that does it draft a response.

Those first steps happen repeatedly. Each has a latency budget, a cost, and a consequence when it goes wrong. A slow router delays every ticket. An unreliable urgency check can bury an outage in the normal queue.

For a PM, the useful question is how much of that workflow can be automated at an acceptable error rate. A model that writes a convincing response solves only part of the problem.

The product: A semantic switch

The mental model I like is a semantic switch. An ordinary switch branches on an exact value. This one interprets messy language before selecting from the branches you have defined.

Think of it as: context + allowed choices → decision + uncertainty.

This is illustrative pseudocode, not the Jev SDK:

result = decide(
    state=customer_email,
    choices=[
        "billing", "technical",
        "sales", "review"
    ]
)

if result.confidence < min_confidence:
    send_to_review(customer_email)
else:
    route_ticket(result.choice)

min_confidence comes from testing on your data. The useful part is that uncertainty changes what the software does.

Jev’s API takes a state, such as the customer email and relevant account details, alongside typed questions. Its documentation describes three primitives:

Primitive What it does Support example
Choice Selects from options you supply Billing, technical support, or sales
Score Evaluates against an ordered rubric Severity from minor inconvenience to service outage
Noul Returns the probability that a yes/no statement is true Is the customer asking to cancel?

You can ask several questions against the same state in one call. That makes the support example easy to picture: read the email once, evaluate its category and urgency, then let application code decide what happens next.

I like the separation of responsibilities. The model interprets messy language. The product team defines the available actions and the conditions for taking them.

It also makes a missing option a product problem. If every ticket must be billing, technical support, or sales, where does an ambiguous complaint go? I would include a review path from the beginning.

Why not use an LLM with structured outputs?

That is a fair alternative. Modern LLM APIs already support schema-constrained responses. OpenAI’s Structured Outputs can enforce a supported JSON schema, including enumerated choices. The comparison has to go beyond whether an answer is valid JSON.

TypeSafe’s bet is that specializing in decisions produces a better combination of speed, cost, and uncertainty estimates. The company describes a parallel sampler and a training method called Reinforcement Learning for Calibrated Decisions. Its launch post reports end-to-end latency of 70 to 500 milliseconds.

Those are vendor results. TypeSafe also notes that its speed tests generally ran from the West Coast, near its service. I would compare it against a small model with structured outputs on the actual workload, including slow requests and escalations. That is the comparison a buyer needs.

There are three differences I would evaluate:

  • The generation overhead. An autoregressive model produces output tokens sequentially, even when the requested answer is a small object. A decision model can avoid that output-generation loop. The benefit depends on the model, input length, and how much output you would otherwise generate.
  • What the confidence number means. Asking a model to write "confidence": 0.95 does not establish that the number is calibrated. Calibration needs to be measured against outcomes. Jev makes probability estimates part of its interface and training objective.
  • Cost per completed decision. Compare input, output, retries, and fallback costs. Jev still needs context and clear questions. The savings have to survive a fair comparison with a well-configured alternative.

Two shifts in how you build

Ask independent questions together

A support system might first classify a ticket, then ask about severity, then check for cancellation intent. If each question can be answered from the original email, those calls do not need to wait on one another.

Jev evaluates questions in parallel against the same state. TypeSafe’s fan-out pattern recommends asking even potentially relevant questions upfront, then using code to decide which answers matter. For a billing ticket, you can ignore the bug-severity result.

That changes how I would design the workflow: identify the independent judgments, ask them together, and keep the branching logic explicit. Questions that depend on newly retrieved information still need a later step.

Let uncertainty change the next step

A decision becomes more useful when the system can tell when to hand it off. Easy tickets can move automatically. Ambiguous ones can go to a stronger model or a person.

There is a detail here that matters. For Choice and Score, Jev’s confidence is a statistic derived from the returned probability distribution. It is not interchangeable with the probability that the selected answer is correct. A confidence value of 0.9 does not, by itself, mean 90% accuracy on your tickets. TypeSafe explains this distinction in its confidence documentation.

My first evaluation would measure automation coverage at an acceptable error rate. How many tickets can move without review while keeping misroutes below the team’s target? Then I would check the result across languages, customer segments, and unusual cases.

Getting an allowed answer also does not guarantee getting the right answer. Jev can choose the wrong category from a perfectly valid list. TypeSafe’s own limitations page is worth reading alongside the launch claims.

What could you actually build?

Support triage across several dimensions

Support triage looks like a sensible entry point. A single email can contain a billing problem, frustration, and a threat to cancel. Asking about each separately preserves information that a single category would lose.

Consider: “You charged us twice, and we are considering moving our whole team elsewhere.” The route may be billing, but cancellation intent should also affect the response. Teams can compare those judgments with existing routing before letting the model act.

Dynamic onboarding and personalization

An application could use recent session context to choose between an onboarding tour, a help prompt, or the standard view. That extends the original idea of a feature flag to decisions based on the meaning of a user’s activity.

I would test this with a latency budget and a default experience if the call times out. A fast model API does not automatically make a fast page load, especially when the network round trip sits in the critical path.

Agent tool selection and action checks

An agent navigating a browser might have a few legal next actions: open a result, fill a field, scroll, or request clarification. Application code can supply that list and use Jev to help select the next step from the page’s text or accessibility tree.

A separate judgment could flag whether a proposed action appears destructive or changes user data. That can be another input to review, but permissions and approval rules still belong in the surrounding system. A confidence score should never grant access to a tool.

Games and simulations

The game-loop example is useful because it makes the latency constraint obvious. Given a character’s health, nearby enemies, and available equipment, the next action might be attack, take cover, retreat, or heal.

TypeSafe’s Doom demonstration uses structured game state, not screenshots. The company also says a conventional bot could play better. What interests me is the possibility of changing behavior through instructions without specifying every situation in a behavior tree.

These examples give the product room to grow. I would still begin with one measurable workflow so the team can see which decisions save effort and which create more review.

The infrastructure angle: What happens when you stop generating text?

There is a hardware reason this idea is interesting.

In a typical autoregressive LLM, inference has two phases. Prefill processes the input in parallel. Decode generates the response token by token. Decode often runs into memory-bandwidth limits, particularly at small batch sizes, because each step needs model weights and cached attention data. NVIDIA’s inference guide explains that distinction.

The model does not recompute the whole conversation from scratch for every token. A KV cache preserves earlier attention calculations. But reading that cache and the weights still takes bandwidth, and sequential generation adds repeated steps. Batching and other serving optimizations can improve utilization.

Jev gives up free-form text generation. My inference is that avoiding the repeated decode loop creates room for a different cost and latency profile. That is a plausible architectural advantage, but it does not establish that Jev always achieves full GPU utilization or eliminates memory bottlenecks.

For an infrastructure buyer, the interesting possibility is doing less work per useful result. If a workflow only needs a decision, specializing the output may remove work that the customer never needed in the first place.

Pricing and the business model

As of September 19, 2026, TypeSafe lists input pricing at $0.042 per million tokens, with free outputs.

To make that concrete: assuming 1,000 total input tokens per call, one million calls would cost $42 in model usage. That is illustrative arithmetic, excluding retries, downstream models, infrastructure, and human review.

The price makes experimentation attractive. It also creates a business challenge. At that assumed request size, a million calls generates only $42 of usage revenue. TypeSafe needs very large volumes, larger workloads, or enterprise contracts to build a substantial business.

The launch post connects Jev’s name to Jevons: making a capability cheaper can increase how much people use it. That is the demand bet here. Teams may add semantic checks to workflows where the economics previously did not work.

What would make this defensible?

My hypothesis is that the durable advantage would be reliable decisions across messy production data, backed by useful uncertainty estimates and consistent service performance. A clean API makes adoption easier. Sustained results make customers stay.

The competitive pressure is real. I would expect buyers to compare Jev with smaller LLMs, task-specific classifiers, and rules for simpler cases. TypeSafe has to keep earning its place in that stack as the alternatives improve.

I am cautiously bullish on the product direction. Giving developers a fast decision API is a clear proposition. The harder proof is whether it reduces the total cost of a successfully completed workflow once mistakes and review are included.

The bigger idea is that more AI could become an ordinary part of application logic: a semantic check inside a workflow, called whenever software needs to interpret something messy. Cheaper, faster decisions could make that practical in many more places.

That is what makes Jev worth watching. I want to see whether the efficiency translates into more work completed correctly, with less intervention.
